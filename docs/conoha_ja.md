# ConoHa の上の onogoro

24 時間働く AI 社員には、住む場所が要る。ConoHa VPS はその住まいに向いている。
この文書は、onogoro がそこに何を足すか、2026-09-27 に何を動かしたか、何が残っているかを書く。
（英語版：[conoha.md](conoha.md)）

## なぜ ConoHa か

24 時間働くエージェントは、止まらないプロセスだ。だから従量課金より定額が効く。

- **円建ての定額。** 時間課金には月額の上限がある。データ転送量で料金は増えない。
- **エージェント用の道具がすでにある。** スタートアップスクリプトが、サーバー作成時に
  Claude Code・n8n・Dify を入れる。
- **公式の MCP サーバーがある**（[gmo-internet/conoha_vps_mcp](https://github.com/gmo-internet/conoha_vps_mcp)、
  リモート版は `https://api.conoha.jp/vps/mcp`）。これで、エージェントが ConoHa を直接操作できる。

ConoHa に無いもの：

- 自前のモデル API
- その MCP サーバーの裏面への備え。**サーバーを 1 台作れるエージェントは、100 台作れる。**

ローカル版の MCP は、API のどのパスにも `conoha_post` と `conoha_delete_by_param` を打てる。
しかも API ユーザーのパスワードを環境変数で持つ。リモート版は OAuth で、パスワードは
エージェントの手に渡らない。それでも、エージェントの手が届く範囲はアカウント全体のままだ。

ConoHa の VPS は停止しても課金される。料金を止める手段は削除だけだ。だから、サーバーを作った
エージェントは、誰かがそれを消すまでお金を使い続ける。

## 鍵について他はどうしているか

| | 認証情報の置き場所 | エージェントを縛るもの |
|---|---|---|
| Cloudflare OS の Gatekeeper | サービスごとの Gatekeeper の中 | リソース単位の狭い API、操作ごとの人の非同期承認 |
| Cloudflare Sandbox の Outbound Worker | 出口。宛先ホストごとにリクエストへ付ける | インスタンスごとの許可・拒否リスト |
| NVIDIA OpenShell の Provider | ゲートウェイ。エージェントはプレースホルダーを持つ | 承認済みの宛先 |
| nono の phantom token | supervisor。エージェントは localhost プロキシ用のセッショントークンを持つ | ドメインの許可リスト |
| **onogoro の harbor（港）** | 同じ VPS 上の `harbor` ユーザー | プラン・台数・月額予算（円）を毎回確かめる。porta が、それ以外の道で ConoHa に届かないようにする |

harbor は、エージェントと同じ場所で動く ConoHa 用の Gatekeeper だ。確かめる上限は、
人が考える単位で書く。月いくらまで、何台まで、どのプランまで。

## VPS 1 台の構成

```
┌─ ConoHa VPS（Ubuntu 24.04）─────────────────────────────────────────────────────────────┐
│                                                                                         │
│  ユーザー harbor                    ユーザー staff                                        │
│  ┌──────────────────────────┐       ┌───────────────────────────────────────────────┐  │
│  │ onogoro harbor  :7707    │◀──────│ supervisor: onogoro → comide                  │  │
│  │ ConoHa API ユーザー(0600)│ token │ モデルの鍵(0600)・役割ごとのシフト(timer)       │  │
│  │ 上限・audit.jsonl        │       │                                               │  │
│  └────────────┬─────────────┘       │   ┌─ worker（道具の呼び出しごと・porta）─────┐ │  │
│               │                     │   │ 役割の作業ディレクトリだけ書ける          │ │  │
│               ▼                     │   │ 空の環境変数：鍵は無い                    │ │  │
│  ConoHa API（compute, volumes）     │   │ 通信：開放、または harbor のポートだけ     │ │  │
│                                     │   └──────────────────────────────────────────┘ │  │
│                                     └───────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

- **3 種類の秘密を、3 か所に分けて置く。**
  - ConoHa の API ユーザーは、`harbor` だけが読める。
  - モデルの鍵は、`staff` だけが読める。使うのは supervisor だけ。
  - harbor のトークンは worker に渡る。上限の範囲のことしかできない。
- **harbor の API：** `GET /` で、できることと今持っているサーバーが分かる。ほかに
  `GET/POST /servers`、`POST /servers/ID/stop|start`、`DELETE /servers/ID`（ブートボリュームも消す）がある。
  - 断るときは 403 を返す。本文に理由と、許すために人が変える設定
    （`ONOGORO_HARBOR_YEN_MONTH=5033`）が入る。モデルはそれを、ふつうの道具の結果として読む。
  - 要求は 1 件ずつ処理する。だから、2 つの要求が同じ予算の枠に両方収まることは無い。
- **harbor が断るもの：**
  - 人が挙げていないプラン
  - 台数の上限を超えるサーバー
  - 予算を超える月額。停止中のサーバーも ConoHa が課金するので、予算に数える
  - 接頭辞の無い名前
  - harbor が作っていないサーバーへの操作
- **`ONOGORO_NET=none` のとき、** porta がコマンドに開くポートは harbor の 1 つだけ
  （`--allow-net 127.0.0.1:7707`）。

## AI 社員

`deploy/conoha/staff/` に、提案メモの 4 体がある。1 体につきファイルは 2 つ：

- `ROLE.md`：指示（日本語）
- `ROLE.env`：スケジュール、通信の可否、harbor を使えるか、誰の報告を読むか

シフトは systemd の timer が起動する
`onogoro -p "$(cat ROLE.md)" --root /srv/staff/ROLE/work --yes` だ。
`--yes` にしてよいのは porta がいるからだ。無人なので、許可の確認に答える人はいない。
代わりにカーネルが答える。

| 役割 | いつ | 通信 | harbor | 読むもの |
|---|---|---|---|---|
| research（リサーチ） | 平日 07:00 | 開放 | 無し | |
| sales（営業サポート） | 平日 09〜18 時、毎時 | 無し | 無し | |
| dev（開発支援） | 平日 10:00, 15:00 | 開放 | 有り | |
| lead（まとめ役） | 平日 18:30 | 無し | 無し | research, sales, dev |

まとめ役は、ほかの役割の outbox の写しを受け取る。書かれたものは読めるが、元のファイルは変えられない。

## 立て方

1. ConoHa VPS（Ubuntu 24.04）を作る。スタートアップスクリプトに `deploy/conoha/startup.sh` を貼る。
   このスクリプトは、下のものを入れ、SSH 以外のポートを閉じ、2 つのユーザーを作る。
   - Almide と porta：リリースバイナリ。チェックサムを確かめる
   - golemide・comide・hew・onogoro：ソースからビルドする
2. SSH で入り、2 つのファイルを埋める。
   - `sudoedit /etc/onogoro/keys.env`：モデルの鍵
   - `sudoedit /etc/onogoro/harbor.env`：ConoHa の API ユーザー、イメージ、ボリューム種別、
     鍵ペア、プランと価格、上限
3. `sudo onogoro-staff enable` を実行する。harbor と、役割ごとの timer が動き出す。

鍵はスタートアップスクリプトに書かない。ConoHa はスクリプトを保存しており、サーバー上で
メタデータサービスに届くものは何でも、それを読み返せるからだ。

## 動かしたこと（2026-09-27）

harbor の dry モード（`ONOGORO_HARBOR_DRY=1`）で動かした。このモードは、サーバーを状態ファイルの
中だけで作り、ConoHa には何も送らない。porta 0.6.16 と comide 0.5.0 は、どちらも main をビルドして使った。

- **`almide test`：** 4 ファイル・11 テストが通る。ポリシー、ConoHa に送る本文、worker の許可を確かめている。
- **harbor を curl で叩いた結果：**
  - トークン無しの要求は 401 になった。
  - 4GB のサーバーは作れた。
  - 2 台目の 4GB は予算超過で断られた。許すための設定も返ってきた。
  - GPU プランは、許可リストに無いので断られた。
  - harbor が作っていないサーバーの削除は断られた。
  - 停止は通った。返答には、停止中も課金されると書かれていた。
  - すべての要求が `audit.jsonl` に残った。
- **経路全体。** 代役のモデルが comide の `shell` ツールに、コマンドを 1 つ実行するよう頼んだ。
  comide はそれを onogoro と porta を通して、通信を閉じ、harbor だけ開けた状態で実行した。
  - 1 台目は作られた。
  - 2 台目は断られ、その理由がツールの結果としてモデルに戻った。
  - worker の中の `env` に鍵は 0 個だった。モデルの鍵も ConoHa のパスワードも見えなかった
    （どちらも supervisor と harbor の環境には設定してあった）。
  - `https://example.com` には届かなかった。

本物の ConoHa アカウントにはまだ触れていない。リクエストは、GMO の MCP サーバーが使うパスと本文に合わせてある。

## 残っていること

- **ConoHa 実機での確認。** 確かめていないことが 4 つある。
  - フレーバー名
  - ブートボリュームの種別
  - サーバーを消したあとブートボリュームが残るか（残るなら課金されるか）
  - 鍵ペアを指定したとき、`adminPass` がランダムでよいか
- **harbor は全インターフェースで待ち受ける。** Almide の `http.serve` が `0.0.0.0` で bind するからだ。
  今は ufw とトークンで閉じているが、本来は `127.0.0.1` で bind する serve が要る。Almide に issue を出す。
- **golemide の鍵。** `solve` には、まだモデルの鍵を名前で渡している。almide/porta#37
  （porta のプロキシにクレデンシャルブローカーを入れる）で解消する。[design](design.md) のとおり。
- **モデルの呼び出しは国外に出る。** worker とデータは VPS に留まる。だが、モデルが読む内容は
  モデルの提供元に届く。「日本から出ない」と言うには、国内でホストされたモデルが要る
  （次節「ConoHa へのお願い」参照）。
- **コーディング以外の社員。** research・sales・lead は、comide の代わりに porta の WASM エージェントチーム
  （`porta agent team.toml`）でも動かせる。
  - 認証情報はホストに残る。
  - 予算はチーム全体で 1 つ。
  - ジャーナルがあるので、途中から再開できる。
  - リモート MCP のツールにはホスト側だけが持つトークンを渡せる。だから ConoHa のリモート MCP を、
    `before_tool_checks` のポリシー付きで許可できる。

  同じ役割で、comide と比べて測る価値がある。

## ConoHa へのお願い

ConoHa にしかできないこと。どれも、harbor を小さくする。

1. **範囲と上限を持つ API トークン。** プラン・台数・月額の上限を、ConoHa 側で守らせる。
   そうなれば全員に harbor があるのと同じで、MCP サーバーにも効く。
2. **停止中はディスク代だけにする。** そうなれば、空いているエージェントを消さずに止める理由ができる。
   Cloudflare の「止めている間は 0 円」への、昼だけ働く社員向けの答えにもなる。
3. **しきい値を超える操作を人が承認する仕組み**を、リモート MCP に。Cloudflare の Gatekeeper と同じ考え方。
4. **国内でホストされたモデルのエンドポイント**（GMO GPU クラウド）。これがあって初めて、
   「サーバーもモデルも請求も、国内・円で一本」が本当になる。
